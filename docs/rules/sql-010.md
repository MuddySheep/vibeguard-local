# SQL-010 — Correlated subquery in SELECT projection

| | |
|---|---|
| **Severity** | `warn` |
| **Confidence** | 70–85 (default 75) |
| **Threat category** | `integrity` |
| **Stable since** | `1.0.0` |

## Pattern

A scalar subquery (`(SELECT ...)`) appears in the outer SELECT's
projection, and the subquery's `WHERE` clause references a column
qualified by an alias / relname from the outer SELECT's `FROM`
clause — the canonical "correlated subquery" shape.

## Why it's worth flagging

Correlated subqueries in projection often produce N+1-shaped query
plans: the subquery executes once per outer row. The pattern is:

- **Easy for an LLM to generate** because it reads naturally
  ("for each user, return the count of their orders")
- **Frequently slower** than the JOIN equivalent on production data
- **Replaceable** with a JOIN + aggregation that the optimizer
  handles in a single scan

The catch is `warn`, not `block`. Sometimes Postgres' planner
optimizes the correlated form into the equivalent join; sometimes
the correlated shape is genuinely the right tool. The catch
surfaces the pattern for human review without forcing a halt.

## Bug example

```sql
-- LLM-generated; almost always slower than the JOIN form below
SELECT
  u.id,
  u.email,
  (SELECT count(*) FROM orders o WHERE o.user_id = u.id) AS n_orders,
  (SELECT max(amount) FROM orders o WHERE o.user_id = u.id) AS top_order
FROM users u;
```

## Correct alternatives

```sql
-- JOIN + aggregation — usually faster, often same number of lines
SELECT
  u.id,
  u.email,
  count(o.id) AS n_orders,
  max(o.amount) AS top_order
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.email;

-- LATERAL join — useful when each outer row needs different
-- per-row computation:
SELECT u.id, u.email, agg.n_orders, agg.top_order
FROM users u
LEFT JOIN LATERAL (
  SELECT count(*) AS n_orders, max(amount) AS top_order
  FROM orders o WHERE o.user_id = u.id
) agg ON true;
```

The LATERAL form retains per-outer-row scoping but expresses it as
a JOIN, which most planners handle better than a correlated SubLink.

## Detection approach

1. Walk to the first `SelectStmt`.
2. Build the set of outer-FROM identifiers via
   `extractFromTables(stmt.fromClause)` — alias if present, else
   relname.
3. For each `ResTarget` in `targetList`:
   - Walk into its `val` looking for `SubLink` nodes with
     `subLinkType = EXPR_SUBLINK` (scalar subquery shape)
   - For each found, walk the subquery's `whereClause`
   - Look for any `ColumnRef` whose first-field qualifier matches
     one of the outer identifiers
   - If found, fire and stop
4. Single-Catch contract: only the first correlated subquery fires.

`'skip'` after evaluating each SubLink prevents nested correlated-
subqueries-of-correlated-subqueries from re-firing. (Future minor
versions can broaden if useful.)

## Confidence justification

**Default 75 / range 70–85.**

Why 75? The shape detection is structural and reliable, but the
"correlation = bug" claim is heuristic. Postgres' planner often
optimizes correlated subqueries into the equivalent join, and some
correlated shapes are genuinely intentional (especially when the
subquery uses a non-mergeable aggregate or a non-deterministic
function).

Why range 70–85? Future minor versions can refine — e.g., raise to
85 when there are MULTIPLE correlated subqueries in projection (the
N+1 cost compounds), or lower to 70 when the subquery returns a
constant scalar (planner usually inlines).

## Known limitations

- **Correlated subqueries in WHERE / HAVING out of scope.** Those
  are often legitimate (e.g. `WHERE EXISTS (...)`, `WHERE col IN
  (correlated)`). Sibling catch possible post-1.0 if there's pull.
- **LATERAL joins not flagged.** The AST shape (`RangeFunction.lateral`
  and `JoinExpr` handling) doesn't go through SubLink, so this rule
  doesn't see them.
- **Single-fire on multi-correlated SELECTs.** Only the first
  correlated subquery fires; documented above.
- **Outer-table CTEs** — a CTE in the outer query (named identifier
  reachable via `extractFromTables`) is treated like a base table
  for correlation detection.
