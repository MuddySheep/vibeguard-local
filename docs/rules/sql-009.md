# SQL-009 — DISTINCT applied to a star projection

| | |
|---|---|
| **Severity** | `info` |
| **Confidence** | 60–75 (default 65) |
| **Threat category** | `integrity` |
| **Stable since** | `1.0.0` |

## Pattern

A `SELECT` statement with plain `DISTINCT` whose every projection
target is a star expansion (`*` or `u.*`).

This is the SDK's first `info`-level catch — designed to surface
"hmm, did you mean it?" patterns rather than block-or-warn-worthy
bugs.

## Why it's worth surfacing

`DISTINCT *` deduplicates rows by full-row equality. In well-formed
data:

- Rows are usually already unique (primary key, surrogate id, or
  natural key)
- Full-row duplicates often signal a bug elsewhere (broken upstream
  ingestion, missing constraint)
- The LLM probably meant to dedupe on a narrower set of columns
  (e.g. unique-by-email) and reached for `DISTINCT *` because it
  parses the way English does

The DISTINCT *isn't dangerous*, just usually wrong. `info` severity
matches that — surface it for human review, don't block or warn.

## Bug example

```sql
-- Probably meant: dedupe by email
SELECT DISTINCT *
FROM users
WHERE active = true;

-- ...the LLM might have meant:
SELECT DISTINCT email FROM users WHERE active = true;
-- or:
SELECT DISTINCT ON (email) * FROM users WHERE active = true ORDER BY email, id;
```

## Correct alternatives

```sql
-- If rows really are unique, just drop DISTINCT:
SELECT * FROM users WHERE active = true;

-- If you want to dedupe by a narrower key, name it:
SELECT DISTINCT email FROM users;

-- If you want one row per group with a chosen "winner" per group,
-- use Postgres-specific DISTINCT ON:
SELECT DISTINCT ON (email) *
FROM users
WHERE active = true
ORDER BY email, created_at DESC;
```

## Detection approach

1. Walk to the first `SelectStmt`.
2. Read `distinctClause`. Suppress if absent / empty.
3. Distinguish plain `DISTINCT` from `DISTINCT ON (cols)`:
   - Plain DISTINCT is encoded as `distinctClause: [{}]` (one
     empty-keyed object)
   - DISTINCT ON is encoded as `distinctClause: [{ColumnRef:{...}}, ...]`
   Suppress on DISTINCT ON.
4. Check `targetList`: every target must be a star reference (its
   `ColumnRef.fields` ends in `A_Star`). If any target is a named
   column, suppress (explicit projection — DISTINCT is deliberate).
5. Otherwise, fire.

The rule fires on the **first** SelectStmt walked. A `DISTINCT *`
inside a subquery (with the outer SELECT not having DISTINCT) won't
trigger because the outer SelectStmt is the first walked.

## Confidence justification

**Default 65 / range 60–75.**

Why 65 and not higher? Because there ARE legitimate uses of
`DISTINCT *`:

- Quick-and-dirty exploration queries
- Datasets known to have row-level dups (deliberately)
- Combining the output of multiple JOINs where the same row appears
  via different paths (here `DISTINCT *` is the right tool)

Why range 60–75? Future minor versions can refine: lower to 60 when
the FROM is a single-table SELECT (DISTINCT * is more clearly
no-op there); raise to 75 when the FROM has multiple JOIN arms
(legitimate-uses are rarer).

## Known limitations

- **Doesn't analyze nested SelectStmt.** A subquery with `DISTINCT *`
  inside an outer SELECT-without-DISTINCT doesn't fire in v1. The
  rule walks to the FIRST SelectStmt only. Sibling rule possible
  post-1.0.
- **Doesn't suggest specific columns.** The fix message points at
  `DISTINCT col` and `DISTINCT ON (col)` but doesn't recommend
  which column. That's by design — the SDK is structural, not
  semantic.
