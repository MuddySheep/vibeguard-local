# SQL-006 — OFFSET without ORDER BY

| | |
|---|---|
| **Severity** | `warn` |
| **Confidence** | 85–95 (default 90) |
| **Threat category** | `integrity` |
| **Stable since** | `1.0.0` |

## Pattern

A `SELECT` statement uses `OFFSET N` (where N is non-zero, non-NULL)
but does not include an `ORDER BY` clause.

## Why it's dangerous

PostgreSQL does not guarantee row order without an explicit `ORDER
BY`. So `OFFSET 100` skips the first 100 rows of an *undefined*
ordering — and "undefined" can change between query runs based on
storage layout, planner choices, parallel query workers, vacuum, and
data churn.

Practical consequences for paginated queries built on this pattern:

- **Page 2 overlaps page 1** — rows from page 1 reappear on page 2
- **Page 2 skips rows** — rows that should appear on page 2 are missed
- The bug is silent — the API returns plausible-looking results
- Often only surfaces under load (parallel workers reorder) or after
  data growth (different layout choices)

## Bug examples

```sql
-- Pagination broken: 'page 2' skips/overlaps with page 1 randomly
SELECT * FROM users LIMIT 10 OFFSET 10;

-- Same bug, parameterized
SELECT * FROM users WHERE active = true OFFSET $1;
```

## Correct alternatives

```sql
-- Deterministic pagination via ORDER BY on a unique column:
SELECT * FROM users
ORDER BY id
LIMIT 10 OFFSET 10;

-- Compound key when individual columns aren't unique:
SELECT * FROM users
ORDER BY created_at, id
LIMIT 10 OFFSET 10;

-- For large datasets, prefer keyset pagination over OFFSET entirely:
SELECT * FROM users
WHERE id > $last_seen_id
ORDER BY id
LIMIT 10;
```

Keyset pagination avoids the linear-scan cost of large OFFSETs and
is recommended for high-volume use.

## Detection approach

1. Walk to the first `SelectStmt`.
2. Read `selectStmt.limitOffset`. If absent → no fire.
3. Suppress on `OFFSET 0` (defensive zero) — `A_Const{ival:{}}` or
   `A_Const{ival:{ival:0}}` shapes.
4. Suppress on `OFFSET NULL` — `A_Const{isnull:true}`.
5. Read `selectStmt.sortClause`. If non-empty array → no fire.
6. Otherwise, fire.

For parameterized offsets (`OFFSET $1`) the rule cannot statically
know whether the parameter is zero. It fires conservatively because
pagination-without-ORDER-BY is broken regardless of the offset value.

## Confidence justification

**Default 90 / range 85–95.**

Why 90 and not 95? The AST signal is structural and unambiguous, but
there are narrow legitimate uses (`OFFSET N` to skip an arbitrary
sample for testing, or as part of intentionally non-deterministic
output). Those uses are rare and almost always benefit from an
explanatory comment, so the warn-level fire is the right protective
default.

Future minor versions can refine — e.g. raise to 95 when the OFFSET
is a constant ≥ 100 (clearly pagination-shaped) and lower to 85 when
the OFFSET is a small constant (might be a test fixture).

## Known limitations

- **Subquery offsets out of scope (v1)** — the rule analyzes only the
  first SelectStmt. An OFFSET inside a CTE / subquery isn't reached
  in v1. Sibling rule possible post-1.0.
- **Set-operation arms** — a UNION arm with OFFSET is treated like
  any other SelectStmt the rule walks to first.
- **`FETCH FIRST N ROWS ONLY` (SQL-standard form)** — Postgres
  supports this as an alias for LIMIT. The rule keys off `limitOffset`
  / `sortClause` regardless of the surface syntax used.
