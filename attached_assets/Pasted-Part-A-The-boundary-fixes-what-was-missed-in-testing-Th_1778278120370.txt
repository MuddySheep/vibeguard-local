Part A — The boundary fixes (what was missed in testing)
These come out of the adversarial test results. Three categories.
Fix #1 — The EXISTS (SELECT *) false positive on SQL-015
What: SELECT id FROM users WHERE EXISTS (SELECT * FROM orders WHERE ...) fires SQL-015. The * inside EXISTS is irrelevant — Postgres optimizes the projection away.
Why it matters: Every ORM (Prisma, SQLAlchemy, Hibernate, ActiveRecord, Sequelize) generates this pattern routinely. If SQL-015 fires on legitimate ORM queries, your false-positive rate looks bad to exactly the audience you're trying to convert.
Severity: Pre-launch fix. Not because it's catastrophic, but because the fix is small and the cost of leaving it in is "first ten ORM users hit it and complain."
The fix: In SQL-015's rule logic, skip the rule when the SELECT * node's parent context is SubLink of type EXISTS_SUBLINK or NOT_EXISTS_SUBLINK. Should be a 5-line AST condition. Add a fixture to your Vitest suite to lock it in.
Fix #2 — Tautological WHERE clauses (the big honest gap)
What: DELETE FROM users WHERE 1=1, UPDATE users SET banned=true WHERE id=id, WHERE id IS NOT NULL on a PK column, WHERE id IN (SELECT id FROM users). All slip through because the analyzer checks "is there a WHERE clause" not "does the WHERE meaningfully filter."
Why it matters: This is the single most common AI footgun pattern. Cursor and Claude Code both produce WHERE 1=1 as a placeholder ("I'll fill this in later") and then forget. It's the failure mode SQL-003 was designed to catch and currently misses.
Severity: Two paths.

Path A (minimum honest fix): Document the boundary in the README. "VibeGuard detects the presence of bounding, not the effectiveness of bounding. WHERE 1=1 will not fire SQL-003." This is the credibility move and costs you an hour. Ship-blocker for launch in the sense that you should not launch without acknowledging it.
Path B (real fix, ship as v1.1.0): Add a literal-tautology detector. Catch the obvious cases: WHERE 1=1, WHERE true, WHERE col = col (same column-ref on both sides), WHERE NOT false. Doesn't require schema awareness. Probably 50-100 lines of AST work. New rule SQL-016 ("WHERE clause is constant-true — equivalent to no filter"), block severity, confidence 95.

I'd ship Path A immediately as part of launch and Path B in v1.1.0 next week. Documenting the limit is itself a feature — most static analyzers oversell.
Fix #3 — Multi-statement deduplication display
What: DROP TABLE a; DROP TABLE b; DROP TABLE c; reports a single SQL-013, not three. The analyzer is correctly processing all three statements; the UI just dedupes.
Why it matters: For an agent-generated migration with multiple destructive ops, the developer sees "1 catch" when there are actually 3 distinct statements they need to review.
Severity: UX nit, not correctness. Post-launch cleanup. Add a count badge: "SQL-013 × 3" or list per-statement.
