# SQL-015 — `SELECT *` over-fetch

| | |
|---|---|
| **Severity** | `info` |
| **Confidence** | 60 |
| **Threat category** | `exfiltration`, `integrity` |
| **Default** | ON |
| **Stable since** | `1.1.0` |

## Pattern

A `SelectStmt`'s projection list contains a `*` — either a bare
`SELECT *` or a qualified `SELECT t.*`. This includes top-level
SELECTs, CTEs, subqueries, and the right-hand side of `UNION` /
`INTERSECT` / `EXCEPT`.

## Why it's dangerous

AI agents over-use `SELECT *` because they don't know the schema.
That has three concrete costs:

1. **Token cost.** Every column in the table round-trips back to the
   agent's context, including columns the agent never reads.
2. **PII surface.** The projection includes every column in the
   table. If any of them are sensitive (a `password_hash`, a
   `ssn`, a `private_notes` field), the entire row is now in the
   agent's context — and likely in any logs or trace stores that
   capture the agent's intermediate state.
3. **Schema-change fragility.** `SELECT *` quietly returns any new
   column the schema gains. The agent's downstream parsing
   (`row.email`, `row.created_at`) doesn't break, but the column
   count and order can drift, breaking ordinal-based consumers
   without an error.

## Bug examples

```sql
-- Agent doesn't know the schema; over-fetches the whole row
SELECT * FROM users WHERE id = $1;

-- Same problem inside a CTE
WITH u AS (SELECT * FROM users) SELECT id FROM u;

-- Qualified-star variant has the same costs
SELECT u.* FROM users u JOIN orders o ON u.id = o.user_id;
```

## Correct alternatives

```sql
-- Name the columns you actually need
SELECT id, email, created_at FROM users WHERE id = $1;

-- For joins, name the columns from each side
SELECT u.id, u.email, o.total FROM users u JOIN orders o ON u.id = o.user_id;

-- For one-off admin / debug queries where you genuinely want every
-- column, keep the star but constrain with a tight LIMIT
SELECT * FROM users LIMIT 5;  -- still fires the catch (info), but
                              -- the small result set bounds the cost
```

## Detection approach

The rule walks the AST looking for `ResTarget` nodes inside a
`targetList`, where the value is a `ColumnRef` whose `fields` array
ends with an `A_Star` marker:

- Bare `*` → `fields: [{A_Star: {}}]`
- Qualified `t.*` → `fields: [{String: {sval: "t"}}, {A_Star: {}}]`

Function-argument stars (`COUNT(*)`, `array_agg(*)`) are deliberately
NOT caught — they are aggregation markers, not projection over-fetch.

The rule fires on the **first** star projection encountered (registry
order, depth-first traversal).

## Confidence justification

**60.** Deliberately mid-range. `SELECT *` is sometimes correct —
generic admin queries, debug prompts, exploratory work where the
schema is the answer. The 60 reflects "very often a footgun,
occasionally intentional"; consumers who want a strict no-star policy
can promote this to a `block` in their own policy layer.

This rule deliberately does NOT use schema metadata to decide if the
projection is wide. The SDK is schema-blind by design — schema-aware
analysis lives in the cloud product, which knows the column count via
the live planner connection. Always-warn at `info` is the disciplined
choice for the static-only OSS path.

## Known limitations

- **`RETURNING *` not caught.** A different threat shape (it surfaces
  all columns of the *affected* rows back to the caller); detecting
  it is a possible follow-up rule but not part of V1.1.
- **No schema-aware threshold.** Rules in the OSS SDK do not have
  access to schema metadata, so the rule cannot say "this table has
  47 columns; that's a bigger over-fetch than the 4-column case."
  Promoting to a schema-aware threshold belongs to the cloud product.
