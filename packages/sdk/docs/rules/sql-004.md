# SQL-004 — Likely implicit type coercion in comparison

| | |
|---|---|
| **Severity** | `warn` |
| **Confidence** | 75–85 (default 75) |
| **Threat category** | `corruption` |
| **Stable since** | `1.0.0` |

## Heads-up — heuristic rule

This is the heaviest-heuristic catch in the SDK. It doesn't have
schema information, so it infers column type from column name. When
column-name conventions don't match the actual schema, you'll see
false positives. Confidence sits at the LOW end of the SDK range
(75) on purpose to communicate that.

If your codebase has lots of false-positives, filter by `confidence`
or `code` in your consumer policy.

## Pattern

A comparison (`=`, `<`, `>`, `<=`, `>=`, `<>`) has:

- One operand that is a bare `ColumnRef` (no TypeCast wrapper)
- The other operand that is a bare `A_Const` literal (no TypeCast)

…and the column name + literal type *disagree* per the heuristic
table:

| Column-name shape | Literal type that fires |
|---|---|
| Numeric-suggesting (`id`, `count`, `total`, `_id`, `_count`, `_amount`, `_size`, `_age`, `_qty`, `_num`, `_price`, `_rank`, `_index`, `_version`) | string |
| Text-suggesting (`name`, `email`, `phone`, `url`, `_name`, `_email`, `_phone`, `_url`, `_text`, `_description`, `_title`, `_label`, `_tag`, `_slug`, `_path`, `_comment`, `_message`) | integer / float |

Date/timestamp columns are explicitly out of scope in v1 — most
legitimate uses are ISO-shape strings, and false-positive cost
exceeds true-positive gain. See "Known limitations" below.

## Why it's dangerous

Implicit coercion in Postgres can:

- **Disable index use.** A numeric column compared to a string forces
  a row-by-row cast, defeating the b-tree index that would otherwise
  short-circuit the lookup.
- **Fail at runtime** on unexpected data. `'abc'::int` throws an error
  Postgres surfaces only when it encounters that row.
- **Produce surprising matches.** Coercion rules between types are
  subtle and the LLM-generated query may match more or fewer rows
  than intended.

## Bug examples

```sql
-- Numeric column vs string literal
SELECT * FROM users WHERE id = 'abc';

-- Suffix-numeric column vs quoted-numeric (still coerces at runtime)
SELECT * FROM orders WHERE total_count > '10';

-- Text column vs numeric literal
SELECT * FROM users WHERE name = 123;
```

## Correct alternatives

```sql
-- Use a literal of the correct type
SELECT * FROM users WHERE id = 123;

-- Or, if the value is genuinely string-shaped at the call site,
-- cast explicitly so the cost is visible to the reader:
SELECT * FROM users WHERE id = '123'::int;

-- For text columns, use string literals
SELECT * FROM users WHERE name = 'alice';
```

## Detection approach

1. Walk every `A_Expr` with `kind = AEXPR_OP` and a comparison
   operator.
2. Find a (ColumnRef, A_Const) pair across `lexpr` / `rexpr` (either
   order). Skip if either operand is a TypeCast, function call, or
   ParamRef — those suppress the catch.
3. Classify the column name against the heuristic table above.
   Skip if no classification matches.
4. Classify the literal kind from the `A_Const` field shape (`sval`
   = string, `ival` = integer, `fval` = float).
5. Apply mismatch matrix; fire on a mismatch.

The catch fires on the **first** mismatch found (single-Catch
contract per `Rule` type).

## Confidence justification

**Default 75 / range 75–85.**

Why 75 default? The AST signal is real (the literal-type detection
is precise and the suppressions for cast / function-call / param are
clean) but the column-type inference is name-based and can mismatch
real schema. We err on the low end to set the right expectations.

Future minor versions can refine — e.g. raise to 85 when the column
name has a *very* strong type signal (`user_id`, `created_at`) and
the literal is *clearly* the wrong type. v1 keeps it at 75 across the
board for simplicity.

## Known limitations

- **No schema info.** The whole rule is column-name-based. Columns
  named `id` that hold a UUID string don't match the heuristic — and
  in fact a quoted UUID literal would *correctly* compare to a UUID
  column, but the rule fires false-positive. Operators with this
  shape can suppress SQL-004 in their consumer policy.
- **Date / timestamp out of scope.** Columns ending in `_at`, `_on`,
  `_date`, `_time` are not classified in v1. Most legitimate uses
  pass ISO-shape strings (`'2024-01-01'`); firing would create more
  noise than signal. Sibling rule possible post-1.0 if it can
  distinguish ISO-shape from non-ISO-shape strings.
- **Catalog drift.** The numeric/text suffix lists are baked in. If
  your codebase has different conventions (e.g. `_no` for numeric,
  `_str` for text), tune via your consumer policy or open an issue
  proposing additions.
- **Single-fire** — only the first mismatch fires per Rule call.
