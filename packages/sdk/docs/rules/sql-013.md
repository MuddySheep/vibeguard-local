# SQL-013 — Destructive DDL (DROP / TRUNCATE)

| | |
|---|---|
| **Severity** | `block` for destructive variants; `warn` for `DROP INDEX` |
| **Confidence** | 99 (block); 85 (warn) |
| **Threat category** | `destruction` |
| **Default** | ON |
| **Stable since** | `1.1.0` |

## Pattern

The query is a destructive Data Definition Language statement:

- `DROP TABLE [IF EXISTS] <name> [CASCADE]`
- `DROP DATABASE [IF EXISTS] <name>`
- `DROP SCHEMA [IF EXISTS] <name> [CASCADE]`
- `TRUNCATE [TABLE] <name> [, <name>...]`
- `DROP INDEX [IF EXISTS] <name>` (lower severity — see below)

## Why it's dangerous

DDL has no `WHERE` clause possibility. The statement either runs and
destroys the named object(s), or it doesn't. There is no scope to add
to soften the operation in place. For an AI-generated query this is
essentially never the intended operation:

- `DROP TABLE users` deletes the table and all its rows. Restoration
  requires a backup.
- `DROP DATABASE production` is a top-level disaster.
- `DROP SCHEMA analytics CASCADE` removes the schema **and** everything
  inside it (tables, views, functions) without further prompting.
- `TRUNCATE` empties a table without firing `DELETE` triggers and is
  not transactionally rollback-able the same way a `DELETE` is in some
  configurations.

`DROP INDEX` is a softer case — operators legitimately drop indexes
during schema maintenance — so it fires at `warn` severity rather
than `block`.

This rule is distinct from
[SQL-003](./sql-003.md) (unbounded UPDATE / DELETE). SQL-003 covers
DML; this rule covers DDL.

## Bug examples

```sql
-- Agent intended to delete one user; emitted DDL by mistake
DROP TABLE users;

-- Agent intended to clear staging data; emitted irreversible DDL
DROP DATABASE staging;

-- CASCADE compounds the damage
DROP SCHEMA analytics CASCADE;

-- Bypasses row triggers, hard to recover from
TRUNCATE accounts;
```

## Correct alternatives

```sql
-- For removing rows, use a scoped DELETE (SQL-003 rejects unbounded forms)
DELETE FROM users WHERE id = 42;

-- For removing all rows when you genuinely need a wipe, route through
-- a migration tool with a confirmation step. Or use the
-- soft-delete-by-rename pattern:
ALTER TABLE users RENAME TO __soft_deleted_users_2026_05_07;
-- (later, after confirming nothing breaks, drop the renamed table
-- through a deliberate maintenance window.)
```

## Detection approach

The rule walks the AST looking for three statement shapes:

- `DropStmt` with `removeType` ∈ { `OBJECT_TABLE`, `OBJECT_SCHEMA`,
  `OBJECT_INDEX` }
- `DropdbStmt` (any — DROP DATABASE has no per-target qualifier)
- `TruncateStmt` (any — TRUNCATE is unambiguously destructive)

Other `DropStmt` shapes (DROP VIEW, DROP FUNCTION, DROP SEQUENCE,
DROP TYPE) are deliberately out of V1.1 scope — they are legitimate
maintenance operations more often than not.

When the rule fires, the catch detail names every dropped/truncated
object (multi-target `DROP TABLE a, b, c` lists `a, b, c`).

## Confidence justification

**99 for DROP TABLE / DROP DATABASE / DROP SCHEMA / TRUNCATE.**
Why so high? The AST signal is unambiguous — these statement types
have no scoping mechanism. Why not 100? There exists a narrow set of
legitimate uses (deliberate database resets, schema-cleanup migrations
run by an operator). Those workflows should pass through a migration
runner or operator-review tool, not be issued by the LLM directly,
so a `block` severity is the right protective default.

**85 for DROP INDEX.** Index drops are routinely-legitimate during
schema maintenance — replacing one index with a better one, dropping
unused indexes to free write capacity. The rule still fires (because
silent index loss can cause severe performance regressions that
Postgres does not warn about) but at the lower `warn` severity.

## Known limitations

- **DROP VIEW / FUNCTION / SEQUENCE / TYPE not caught.** These are
  out of V1.1 scope. They tend to be legitimate maintenance more
  often than mistakes; future rule additions may cover them with
  per-type confidence scores.
- **ALTER TABLE ... DROP COLUMN not caught** — different statement
  type (`AlterTableStmt` with a `DROP COLUMN` subtype). Its own
  catch if added later.
- **DROP USER / DROP ROLE not caught** — permissions live in the
  cloud product, outside the SQL-* SDK scope.
