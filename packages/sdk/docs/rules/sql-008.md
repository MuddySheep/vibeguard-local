# SQL-008 — Possible string-concatenation injection

| | |
|---|---|
| **Severity** | `block` |
| **Confidence** | 80–90 (param-bearing concat = 90, mixed-shape = 80) |
| **Threat category** | `injection` |
| **Stable since** | `1.0.0` |

## Heads-up — block severity by design

This catch fires on shapes that *look like* SQL injection even when
they aren't (e.g. `$1 || '%'` for a LIKE pattern). The decision to
fire at `block` severity is deliberate:

- **True-positive cost** of letting a real injection through: full
  data compromise, including read AND write
- **False-positive cost** of blocking a legitimate concat: the LLM
  is asked to rewrite using parameterized values — harmless

The asymmetry justifies firing aggressively. Operators with a known
heavy-display-concat codebase can suppress in their consumer policy.

## Pattern

A string concatenation operator (`||`) combines two or more operands
where at least one operand is **not** a literal string and **not** a
plain column reference.

The detector flattens left-associative concat chains
(`'a' || $1 || 'b' || c` → 4 operands), classifies each, and applies
this matrix:

| Operand mix | Action |
|---|---|
| All literals | Suppress — pure literal concat is harmless |
| Any array literal (`ARRAY[...]`) | Suppress — Postgres `||` is also array-concat; we can't statically tell which overload applies, so we side with safety on legitimate array use |
| All operands are column-or-literal | Suppress — display concat shape (`first || ' ' || last`) is legitimate |
| Any param (`$1`) | Fire at confidence **90** |
| Mix involves a function call or other shape | Fire at confidence **80** |

## Why it's dangerous

Building SQL fragments via concatenation is the canonical injection
vector. Even when an LLM "uses parameters," concatenating them with
literal SQL fragments often re-introduces the vulnerability:

```sql
-- Looks safe because $1 is "parameterized" — but isn't:
EXECUTE 'SELECT * FROM users WHERE name = ''' || $1 || '''';
```

In the AI-agent context, the LLM may not distinguish between
"parameter for a value position" (safe) and "parameter for an
identifier position" (unsafe). The catch errs toward making *both*
patterns visible.

## Bug examples

```sql
-- Param + literal concat — classic injection shape
SELECT * FROM users WHERE id = ('AND name=' || $1 || '');

-- Multi-segment param concat (worst kind — many interpolation points)
INSERT INTO logs (msg)
VALUES ('error: ' || $1 || ' from ' || $2);

-- Param concat for a LIKE pattern (legitimate intent, dangerous shape)
SELECT * FROM users WHERE name = $1 || '%';
```

## Correct alternatives

```sql
-- Pure parameterized comparison
SELECT * FROM users WHERE id = $1;

-- LIKE with the wildcard appended in the application layer:
-- application: const pattern = userInput + '%';
SELECT * FROM users WHERE name LIKE $1;

-- Or LIKE with concat done server-side in a controlled way:
SELECT * FROM users WHERE name LIKE ($1 || '%');
-- (still fires SQL-008; consumer can suppress if they trust this shape)

-- Display concat from columns is allowed (rule does not fire):
SELECT first_name || ' ' || last_name AS full_name FROM users;
```

## Detection approach

1. Walk every `A_Expr` with `kind = AEXPR_OP` and operator `||`.
2. Recursively flatten the concat tree into a flat operand list.
3. Classify each operand:
   - `A_Const` → literal
   - `ParamRef` → param
   - `ColumnRef` → column
   - `A_ArrayExpr` → array
   - anything else → other
4. Apply suppression / fire matrix above.
5. Fire only on the **first** non-suppressed concat per Rule call
   (single-Catch contract).

The walker uses `'skip'` after evaluating each `||` chain so nested
inner `||` operators (already flattened) aren't double-counted.

## Confidence justification

**Param operand → 90.** The AST signal is precise: any `||` with a
ParamRef is in the dangerous shape, regardless of the surrounding
context. False-positive surface is real (LIKE patterns) but bounded.

**Function-call mix → 80.** The shape is more ambiguous (function
results could be safe or unsafe depending on the function), so the
rule flags conservatively at a lower confidence to communicate that
to consumers.

## Known limitations

- **LIKE-pattern false-positives** — `$1 || '%'` is a legitimate
  pattern construction; the rule still fires. Suppress in consumer
  policy if your codebase frequently uses this shape.
- **Array vs string ambiguity** — `||` is overloaded. Without schema
  info, we can't tell whether an operand is a string or array. The
  rule treats `A_ArrayExpr` operands as a strong "not string concat"
  signal and suppresses; this means any concat containing an array
  literal won't fire. Edge cases (e.g. `column || ARRAY[...]` where
  the column is a string and the array is mistakenly there) won't
  fire. Acceptable for v1.
- **EXECUTE inside PL/pgSQL** — the canonical injection shape is
  `EXECUTE '...' || dynamic`. PL/pgSQL function bodies aren't parsed
  by libpg-query at the SQL level; this rule operates on top-level
  SQL. Sibling catch possible post-1.0 if libpg-query exposes the
  PL/pgSQL parse tree.
- **Single-fire** — only the first match fires per Rule call.
