# SQL-008 — Possible string-concatenation injection

| | |
|---|---|
| **Severity** | `block` (CASE 1) / `info` (CASE 2) |
| **Confidence** | 75–90 (CASE 1 = 80 or 90; CASE 2 = 75) |
| **Threat category** | `injection` |
| **Stable since** | `1.0.0` (CASE 2 added in `1.6.0` — purely additive) |

## Two-tier detection

SQL-008 fires in two distinct cases at different confidence/severity
calibrations. The split exists because string-concat shapes range
from "actively exploitable at runtime" to "constant-folded but the
shape is exactly what an LLM produces when it's about to introduce
an injection vector."

### CASE 1 — runtime-injection shape (`block`)

**Unchanged from v1.5.** A `||` chain where at least one operand is
**not** a literal A_Const and **not** a column reference. Param refs
fire at confidence **90**; function-call or other-shape mixes fire at
confidence **80**.

This is the actually-exploitable shape: the value placed into the
SQL fragment is not constant-foldable, so an attacker-controlled
value can change the meaning of the query.

### CASE 2 — pure-literal injection-payload shape (`info`, confidence **75**)

**New in v1.6 — purely additive (no v1.5 silent shape was reclassified
out of CASE 2's coverage; the rule simply fires on more queries
than it did before).**

A `||` chain where every operand is a literal A_Const, **and** at
least one literal contains an injection-payload signature:

```re
/\b(OR|UNION|DROP|TRUNCATE|DELETE|EXEC|EXECUTE)\b|--|;\s*\w|\b1\s*=\s*1\b|'\s*=\s*'/i
```

The query as written is constant-folded by the parser and is not
exploitable at runtime, but the *shape* — concatenating SQL fragments
that contain payload-flavored text — is the unmistakable footprint of
injection-style code authoring. Worth a manual review of how the
surrounding code came to produce this query (often: an LLM was about
to introduce a real injection vector and was halfway through writing
it; the pure-literal version is the "test fixture").

`info` severity is the right calibration: don't cry wolf on something
that's not exploitable as written, but make sure the reviewer sees it.

### CASE 3 — pure-literal benign concat (suppressed)

All operands literal, no payload signature. Examples:

```sql
SELECT 'a' || 'b' AS x FROM users;                   -- silent
SELECT 'foo' || 'bar' FROM t;                        -- silent
UPDATE users SET note = 'hello ' || ' world';        -- silent
```

Constant-folded AND no injection-shape footprint. Silent.

### Array operands — suppressed at every tier

Postgres `||` is overloaded: it's also array concatenation. Without
schema info we can't tell which overload applies, and an array
operand is a strong signal that the call site is array-concat, not
string-concat. Any `||` chain containing an `A_ArrayExpr` operand is
silent.

### Display concat — suppressed

Column refs concatenated with literals (e.g. `first_name || ' ' ||
last_name`) is the legitimate display-concat shape. Silent regardless
of literal contents.

## Operand classification matrix

| Operand mix | Action |
|---|---|
| Any array literal (`ARRAY[...]`) | Suppress |
| Any param (`$1`) | Fire CASE 1 — `block` / **90** |
| All literals + payload regex match | Fire CASE 2 — `info` / **75** |
| All literals + no payload match | Suppress (CASE 3) |
| Mixed column + literal (no param, no other) | Suppress (display concat) |
| All columns | Suppress (display concat) |
| Function-call / other shape mix (no param) | Fire CASE 1 — `block` / **80** |

CASE 1 wins over CASE 2 when both could apply (e.g. `$1 || ' OR
1=1'` — has a ParamRef AND the literal contains a payload signature
— fires `block`/90, not `info`/75). The runtime-exploit shape is
the more important signal.

## Why it's dangerous

Building SQL fragments via concatenation is the canonical injection
vector. Even when an LLM "uses parameters," concatenating them with
literal SQL fragments often re-introduces the vulnerability:

```sql
-- Looks safe because $1 is "parameterized" — but isn't:
EXECUTE 'SELECT * FROM users WHERE name = ''' || $1 || '''';
```

In the AI-agent context, the LLM may not distinguish between
"parameter for a value position" (safe) and "parameter for an
identifier position" (unsafe). The catch errs toward making *both*
patterns visible.

## Bug examples

```sql
-- CASE 1: param + literal concat — classic injection shape (block/90)
SELECT * FROM users WHERE id = ('AND name=' || $1 || '');

-- CASE 1: multi-segment param concat (worst kind) (block/90)
INSERT INTO logs (msg) VALUES ('error: ' || $1 || ' from ' || $2);

-- CASE 1: param concat for a LIKE pattern (block/90)
SELECT * FROM users WHERE name = $1 || '%';

-- CASE 1: function-call mix (block/80)
SELECT col || to_char(now(), 'YYYY-MM-DD') FROM t;

-- CASE 2: pure-literal payload shape (info/75 — constant-folded, but
-- the SHAPE is the smell)
SELECT * FROM users WHERE name = 'admin' || ' OR 1=1';
```

## Correct alternatives

```sql
-- Pure parameterized comparison
SELECT * FROM users WHERE id = $1;

-- LIKE with the wildcard appended in the application layer:
-- application: const pattern = userInput + '%';
SELECT * FROM users WHERE name LIKE $1;

-- Display concat from columns is allowed (rule does not fire):
SELECT first_name || ' ' || last_name AS full_name FROM users;
```

## Detection approach

1. Walk every `A_Expr` with `kind = AEXPR_OP` and operator `||`.
2. Recursively flatten the concat tree into a flat operand list.
3. Classify each operand: `A_Const` → literal, `ParamRef` → param,
   `ColumnRef` → column, `A_ArrayExpr` → array, anything else → other.
4. Apply the matrix above:
   - Array → skip
   - Any param → CASE 1 fire (block/90)
   - All literal + payload regex → CASE 2 fire (info/75)
   - All literal, no payload → skip (CASE 3)
   - All column/literal mix → skip (display)
   - Otherwise → CASE 1 fire (block/80)
5. Fire only on the **first** non-suppressed concat per Rule call
   (single-Catch contract).

The walker uses `'skip'` after evaluating each `||` chain so nested
inner `||` operators (already flattened) aren't double-counted.

## Stability note (v1.6 — purely additive)

v1.6 is **purely additive** to SQL-008. Every query that fired SQL-008
in v1.5 still fires in v1.6 at **the same severity and the same
confidence**. CASE 2 only adds NEW fires for pure-literal concat
chains containing payload signatures (which were silent in v1.5).

No v1.5 fixture was reclassified, downgraded, or upgraded. STABILITY.md
compliance: minor-version expansion of detection coverage with no
severity changes.

## Known limitations

- **LIKE-pattern false-positives** — `$1 || '%'` is a legitimate
  pattern construction; CASE 1 still fires. Suppress in consumer
  policy if your codebase frequently uses this shape.
- **Payload regex tuning** — the CASE 2 signature catches obvious
  payload words (`OR`, `UNION`, `DROP`, ...) but is not exhaustive.
  Refine if false-positive reports come in for legitimate copy that
  happens to contain these tokens.
- **Array vs string ambiguity** — `||` is overloaded. Without schema
  info, we can't tell whether an operand is a string or array. The
  rule treats `A_ArrayExpr` operands as a strong "not string concat"
  signal and suppresses.
- **EXECUTE inside PL/pgSQL** — the canonical injection shape is
  `EXECUTE '...' || dynamic`. PL/pgSQL function bodies aren't parsed
  by libpg-query at the SQL level; this rule operates on top-level
  SQL. Sibling catch possible post-1.0 if libpg-query exposes the
  PL/pgSQL parse tree.
- **Single-fire** — only the first match fires per Rule call.
