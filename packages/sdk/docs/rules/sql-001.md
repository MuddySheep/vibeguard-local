## Pattern

A `SELECT` references two or more tables in its `FROM` clause without
an explicit `JOIN` and without a `WHERE` predicate that relates the
tables. The result is the cartesian product of every listed table.

## Why it's dangerous

For tables of N and M rows, the result row count is N × M. On
production data, the multiplicative growth easily reaches billions of
rows for queries that the LLM expected to return thousands. This:

- Exhausts memory on the database server
- Blocks other connections waiting on shared resources
- Can take down the database instance entirely
- Often happens silently — the query "completes" but returns far more
  data than the application can sensibly handle

In the AI-agent context, this pattern usually means the LLM forgot the
join predicate. Catching it before execution is essentially free
compared to the cost of cleaning up after a runaway query.

## Bug example

```sql
SELECT *
FROM users, orders;
```

100 000 users × 1 000 000 orders = **100 billion** result rows.

## Correct alternatives

```sql
-- Explicit JOIN with predicate:
SELECT *
FROM users u
JOIN orders o ON u.id = o.user_id;

-- Or a WHERE-clause join predicate:
SELECT *
FROM users u, orders o
WHERE u.id = o.user_id;

-- Or, if the cross product is genuinely intended, be explicit:
SELECT *
FROM users CROSS JOIN orders;
```

The third form (`CROSS JOIN`) is the documented way to say "I really
mean cartesian." `SQL-001` honors it and does not fire — the
explicitness moves responsibility for the consequences onto the
author.

## Detection approach

The rule walks to the first `SelectStmt` encountered in the AST and
applies a four-step check. The catch fires when **all four** are true:

1. `SelectStmt.fromClause` references ≥ 2 distinct table-shaped items
   (`RangeVar` or `RangeSubselect` after substrate extraction)
2. There is no `JoinExpr` anywhere in the `fromClause` subtree
3. The `whereClause` (if present) does not contain a binary comparison
   (`A_Expr`) whose two operands are `ColumnRef`s with two different
   table qualifiers, both of which identify tables in our FROM set
4. (Implicit) The first statement encountered is a `SelectStmt`;
   UPDATE / DELETE statements aren't analyzed by this rule

## Confidence justification

**Default 95** — the AST signal is structural and unambiguous: there
are joins or there aren't. The narrow band (90–95) accommodates future
minor versions that may downgrade to 90 when a heuristic in step 3
fires (e.g. a possible cross-table predicate that the rule couldn't
statically confirm relates ALL listed tables).

We do not fire above 95 because there is a small set of legitimate
cartesian uses (intentional combinatorics, data tiling for testing).
Those should be expressed via `CROSS JOIN`, but a query author may
not get there immediately.

## Known limitations

The detection is conservative — when in doubt, the rule fires. Some
patterns the v1 rule does NOT catch (false negatives):

- Cartesian inside a non-top-level `SelectStmt` (subquery, UNION arm)
  — the rule analyzes only the first `SelectStmt` it walks to. Future
  minor versions can broaden this.
- `FROM users u JOIN orders o ON 1=1` — has a `JoinExpr` (so the rule
  suppresses) but the `ON 1=1` predicate is a tautology. Detecting
  tautologies is its own catch, post-1.0.

Some patterns the rule DOES fire on conservatively (potential false
positives):

- `FROM users u, orders o WHERE NOT EXISTS (SELECT 1 ...)` — the
  EXISTS clause does relate the tables semantically, but only via
  subquery semantics that AST-level inspection can't fully verify.
- `FROM users u, orders o WHERE id = 1` — bare `id` without a
  qualifier could mean either table; the rule treats this as
  ambiguous and fires.

In both cases the resolution is to add an explicit `JOIN ... ON` or
qualify the predicate's columns. The cost is one rewrite; the benefit
is a strong, predictable signal.
