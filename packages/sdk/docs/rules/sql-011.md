# SQL-011 — Aggregate with non-aggregated column and no GROUP BY

| | |
|---|---|
| **Severity** | `warn` |
| **Confidence** | 85–95 (default 90) |
| **Threat category** | `corruption` |
| **Auto-fix** | yes — adds `GROUP BY <missing column>` named after the first naked (non-aggregated) column. Inserted before any `HAVING` / `ORDER BY` / `LIMIT` / `OFFSET` clause; appended to end-of-statement otherwise. Preserves qualified column names (`t.name`). |
| **Stable since** | `1.0.0` (rule); `1.3.0` (autofix) |

## Pattern

A `SELECT` mixes an aggregate function (`count`, `sum`, `avg`,
`string_agg`, etc.) with a non-aggregated column reference, and
there is no `GROUP BY` clause to bind the non-aggregated column
to a group.

Postgres rejects this at runtime with the famous error:

> column "..." must appear in the GROUP BY clause or be used in an aggregate function

The catch surfaces it pre-execution.

## Bug example

```sql
-- Postgres errors at runtime:
SELECT count(*), name FROM users;

-- Same shape, longer projection:
SELECT count(*), name, max(amount) FROM orders;
```

## Correct alternatives

```sql
-- Add GROUP BY:
SELECT count(*), name FROM users GROUP BY name;

-- Or aggregate the bare column:
SELECT count(*), max(name) FROM users;

-- Or, if the bare column isn't actually needed, drop it:
SELECT count(*) FROM users;
```

## Detection approach

1. Walk to the first `SelectStmt`.
2. Suppress if `groupClause` is non-empty (GROUP BY present).
3. For each entry in `targetList`, do a state-tracking DFS:
   - When a `FuncCall` is encountered, check:
     - `over` field set → window function (e.g. `count(*) OVER ()`):
       descend into its arguments with `insideAggOrWindow=true` so
       column refs inside don't count as naked
     - else if name matches the aggregate catalog → it's an aggregate.
       Mark `hasAggregate=true` and descend with
       `insideAggOrWindow=true`
     - else (regular function) → descend without changing state
   - When a `ColumnRef` is encountered:
     - if `insideAggOrWindow=false` → mark `hasNakedColumn=true`
     - otherwise → ignore (it's inside an aggregate or window)
4. Fire only when both `hasAggregate` AND `hasNakedColumn` are true.

The catalog of aggregate names is the **public Postgres built-in
list**: `count, sum, avg, min, max, string_agg, array_agg, json_agg,
jsonb_agg, json_object_agg, jsonb_object_agg, bool_and, bool_or,
every, bit_and, bit_or, xmlagg, corr, covar_pop, covar_samp, stddev,
stddev_pop, stddev_samp, variance, var_pop, var_samp, mode,
percentile_cont, percentile_disc`. User-defined aggregates registered
via `CREATE AGGREGATE` aren't in the catalog and won't trigger the
rule (false-negative; documented).

## Confidence justification

**Default 90 / range 85–95.**

Why 90? The signal is structural and unambiguous (aggregate +
non-aggregated column without GROUP BY). The rule fires only on
shapes Postgres will reject at runtime — there's no semantic
ambiguity to introduce false positives.

Why range 85–95? Future minor versions can refine confidence based
on:
- Aggregate catalog hits (which aggregate fired) — some are stronger
  signals than others
- The `over` field detection accuracy across libpg-query versions
- Schema-qualified aggregate names (`pg_catalog.count(*)`) — the
  rule reads the LAST funcname component, so qualified calls work,
  but rare parser-version differences could shift this

## Known limitations

- **User-defined aggregates** — `CREATE AGGREGATE my_agg(...)` won't
  match the catalog. The rule won't fire on a query that mixes
  `my_agg(*)` with a naked column. Schema introspection would solve
  this; out of scope for the SDK (cloud product territory).
- **Window functions** — `count(*) OVER (...)` correctly suppresses
  via the `over`-field check. Verified by negative tests.
- **Subquery scalars in projection** — `(SELECT max(x) FROM t)` is
  a subquery, not a naked ColumnRef of the outer SELECT, so it
  doesn't trigger naked-column detection. Verified.
- **HAVING aggregates** — only `targetList` is analyzed for
  aggregate vs naked-column detection. HAVING-only aggregates
  without targetList aggregates are not surfaced (rare shape).
