# SQL-007 — NOT IN with potentially-nullable subquery

| | |
|---|---|
| **Severity** | `warn` |
| **Confidence** | 75–85 (default 80) |
| **Threat category** | `corruption` |
| **Stable since** | `1.0.0` |

## Pattern

`WHERE x NOT IN (SELECT col FROM ...)` where the subquery projection
is not explicitly guarded against NULL via:

- `WHERE col IS NOT NULL` predicate inside the subquery, OR
- The projection wrapping the column in a NULL-safe function
  (`coalesce`, `nullif`, `ifnull`)

## Why it's dangerous

In SQL's three-valued logic, `x NOT IN (..., NULL, ...)` always
evaluates to **UNKNOWN** (treated as false). When a subquery
projection might return NULL, the entire `NOT IN` filter silently
returns nothing — even for rows that are obviously not in the
subquery's result.

A textbook footgun. The bug is silent: the query "works," but
returns wrong results.

## Bug example

```sql
-- If banned.user_id has even one NULL row, this returns ZERO users:
SELECT *
FROM users
WHERE id NOT IN (SELECT user_id FROM banned);
```

## Correct alternatives

```sql
-- Add the IS NOT NULL guard to the subquery
SELECT *
FROM users
WHERE id NOT IN (SELECT user_id FROM banned WHERE user_id IS NOT NULL);

-- Or coalesce to a sentinel
SELECT *
FROM users
WHERE id NOT IN (SELECT coalesce(user_id, 0) FROM banned);

-- Best: rewrite as NOT EXISTS — NULL-safe by construction
SELECT *
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM banned b WHERE b.user_id = u.id
);
```

`NOT EXISTS` is the recommended pattern: structurally NULL-safe and
often a better optimizer plan choice in Postgres.

## Detection approach

1. Walk every `BoolExpr` with `boolop = NOT_EXPR`.
2. For each, check if any `args[i]` is a `SubLink` with
   `subLinkType = ANY_SUBLINK` — this is the AST encoding of
   `NOT (x = ANY (subquery))`, which Postgres uses for `NOT IN`
   subquery shapes.
3. Read the subquery's first projected column name. If the
   projection is a NULL-guarding function (`coalesce`, `nullif`,
   `ifnull`), suppress.
4. Walk the subquery's `whereClause` looking for a `NullTest` node
   with `nulltesttype = IS_NOT_NULL` whose `arg.ColumnRef` matches
   the projected column name.
5. If no guard is found, fire.

The catch fires on the **first** matching pattern (single-Catch
contract per Rule type).

`NOT IN (1, 2, 3)` (literal list) uses a different AST encoding
(`A_Expr` with `kind = AEXPR_IN`, name `<>`) and never enters this
rule's path. `NOT EXISTS (SELECT ...)` is also a different shape
and doesn't fire.

## Confidence justification

**Default 80 / range 75–85.**

Why 80? The shape detection is reliable (BoolExpr+NOT, SubLink+ANY)
and the guard-detection covers the most common forms. False
positives can occur when:

- The user uses a non-standard guard like `WHERE col > 0` (which
  implies NOT NULL but the rule doesn't recognize)
- A schema-NOT-NULL constraint guarantees the column never returns
  NULL (we have no schema info)

Why range 75–85? Future minor versions can refine — e.g. drop to 75
when the suppression heuristics get smarter (recognize `> 0`,
`IS DISTINCT FROM NULL`, etc.), or raise to 85 when the projection
column name is something semantically NULL-prone like `manager_id`,
`parent_id`.

## Known limitations

- **Implicit NULL guards** — `WHERE col > 0` implies NOT NULL but
  isn't recognized. False-positive surface.
- **Schema-aware NULL detection** — out of scope without DDL info.
- **Composite NOT IN** — `(a, b) NOT IN (SELECT a, b FROM ...)` —
  v1 reads only the first projection column; secondary nullability
  isn't analyzed.
- **Subquery descent depth** — capped by the substrate's
  `AST_WALK_MAX_DEPTH` (1000). Adversarial pathological depths halt
  cleanly without crashing.
