# SQL-012 — Recursive CTE without obvious termination

| | |
|---|---|
| **Severity** | `block` |
| **Confidence** | 80–95 (default 85) |
| **Threat category** | `denial-of-service` |
| **Stable since** | `1.0.0` |

## Pattern

A `WITH RECURSIVE` CTE has:

- A self-referencing recursive arm (the CTE body's `rarg` of a
  `UNION ALL` shape contains a `RangeVar` referencing the CTE name)
- No comparison against a numeric constant in the recursive arm's
  `WHERE` clause (the heuristic for "this recursion will terminate")

## Why it's dangerous

Without an explicit termination condition, a recursive CTE iterates
unboundedly until Postgres exhausts memory. This is a denial-of-
service shape — the database can't gracefully recover from running
out of memory mid-query.

In the AI-agent context, the LLM may have generated the recursion
intending the `UNION ALL` to "naturally terminate," not realizing
that without a bounding predicate, the recursion never stops.

## Bug examples

```sql
-- No termination — runs until OOM
WITH RECURSIVE r AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM r
)
SELECT * FROM r;

-- Only LIMIT on outer query — recursion is still unbounded
WITH RECURSIVE r AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM r
)
SELECT * FROM r LIMIT 100;
```

## Correct alternatives

```sql
-- Bound by depth-counter literal
WITH RECURSIVE r AS (
  SELECT 1 AS n
  UNION ALL
  SELECT n + 1 FROM r WHERE n < 100
)
SELECT * FROM r;

-- Tree walk with explicit depth column to enforce a max
WITH RECURSIVE r AS (
  SELECT id, 0 AS depth FROM start
  UNION ALL
  SELECT t.child_id, r.depth + 1
  FROM r JOIN tree t ON t.parent = r.id
  WHERE r.depth < 10
)
SELECT * FROM r;
```

## Detection approach

1. Walk every `WithClause` with `recursive: true`.
2. For each `CommonTableExpr` in the WITH:
   - Read `cteName` and the body (`ctequery.SelectStmt`).
   - Verify the body is a UNION shape (`op = SETOP_UNION`).
   - Take the recursive arm (`rarg`) and look for a self-reference
     (a `RangeVar` whose `relname === cteName`) anywhere in its
     `fromClause`. If absent → not actually recursive, suppress.
   - Walk the recursive arm's `whereClause` looking for an `A_Expr`
     with `kind = AEXPR_OP` and a comparison operator
     (`<`, `<=`, `>`, `>=`, `=`, `<>`) where at least one operand is
     a numeric `A_Const` literal.
   - If no such bounding predicate exists → fire.

The catch fires on the **first** unbounded recursive CTE found
(single-Catch contract per Rule type).

## Confidence justification

**Default 85 / range 80–95.**

Why 85 (not higher)? "Will this recursion terminate?" is the halting
problem in general — we can prove "no obvious bounded predicate" but
not "this will run forever." Some legitimate recursion patterns
terminate via data shape (e.g. tree walks where the parent-child
chain naturally bottoms out). The rule fires false-positively on
those.

Why 85 (not lower)? The structural signal is real: WITH RECURSIVE +
self-reference + no constant-bounded predicate is a *very* common
unbounded shape, and the cost asymmetry favors firing — false-
positive forces a depth-counter (cheap insurance even when the
recursion is naturally bounded); false-negative could DoS production.

Why range 80–95? Future minor versions can refine — drop to 80 when
the recursive arm has a JOIN to a definitely-finite table; raise to
95 when there's an explicit infinite shape (e.g. `UNION ALL SELECT
n+1 FROM r` with no WHERE at all).

## Known limitations

- **Halting-problem-equivalence.** We can't statically prove
  termination in general. Conservative fire is the design choice.
- **Bounding via JOIN to finite table.** A query like
  `... FROM r JOIN tree ON tree.parent = r.id` (where `tree` is a
  finite table) terminates by data shape but the rule fires
  conservatively. Document.
- **Bounding via `IS NULL`.** A recursion that terminates via
  `WHERE r.parent_id IS NULL` (climbing a parent chain) doesn't
  use a constant comparison; the rule fires. Acknowledged false-
  positive.
- **Single-fire** — only the first unbounded recursive CTE per
  Rule call.
- **Depth-cap fallback.** Even when the rule false-positives,
  adding an explicit depth column is cheap insurance and good
  hygiene. The fix message recommends it explicitly.
