# SQL-003 — Unbounded UPDATE / DELETE statement

| | |
|---|---|
| **Severity** | `block` |
| **Confidence** | 95–99 (UPDATE = 99, DELETE = 97) |
| **Threat category** | `destruction` |
| **Stable since** | `1.0.0` |

## Pattern

An `UPDATE` or `DELETE` statement has no `WHERE` clause. Every row in
the target table is affected.

## Why it's dangerous

For an AI-generated query, this is virtually always a bug. The LLM
intended to scope the operation ("update the user with id 42") and
forgot the predicate. The result on production data:

- `UPDATE users SET email = 'x'` overwrites every user's email with
  the same value
- `DELETE FROM users` empties the table

These are unrecoverable without a backup. Catching at pre-flight is
essentially free compared to the cost of a restore.

## Bug examples

```sql
-- Forgotten WHERE on UPDATE — overwrites every row
UPDATE users SET email = $1;

-- Forgotten WHERE on DELETE — empties the table
DELETE FROM orders;
```

## Correct alternatives

```sql
-- Scope the update to specific rows
UPDATE users SET email = $1 WHERE id = $2;

-- Scope the delete
DELETE FROM orders WHERE created_at < now() - interval '90 days';

-- If you genuinely want to wipe a table, use TRUNCATE — it's
-- the unambiguous opt-in:
TRUNCATE TABLE staging_imports;
```

`TRUNCATE` is a separate statement type that SQL-003 doesn't analyze.
Using it expresses intent clearly: "I really mean delete every row."

## Detection approach

The rule walks the AST and looks for:

- `UpdateStmt` nodes with no `whereClause` field, OR
- `DeleteStmt` nodes with no `whereClause` field

When found, the catch fires with severity `block`. UPDATE gets
confidence **99** (stronger signal — UPDATE-without-WHERE is even more
suspicious than DELETE-without-WHERE because intentional table-wipes
usually go through TRUNCATE). DELETE gets **97**.

For multi-statement scripts (e.g.
`UPDATE a SET x=1; UPDATE b SET x=1 WHERE y=2`) the rule fires on the
**first** unbounded statement encountered. v1 returns a single Catch
per `Rule` invocation. Future enhancement: batch-fire on all
unbounded statements in a multi-stmt script.

## Confidence justification

**99 for UPDATE / 97 for DELETE.**

Why so high? The AST signal is binary — `whereClause` is either there
or it isn't. There's no heuristic.

Why not 100? Because there's a narrow set of legitimate uses (admin
scripts that intentionally update every row, e.g.
`UPDATE settings SET version = 2`). Those should usually be reviewed
by a human anyway, so a `block`-severity catch is the right protective
default. Operators can downgrade to a non-blocking warning in their
own policy if their workflow tolerates table-wide writes.

DELETE confidence is one notch lower because table-wide DELETEs are
slightly more common in legitimate flows (clearing a test table,
admin-script flush). The asymmetry communicates that to downstream
consumers reading confidence numerically.

## Known limitations

- **`WHERE TRUE` / `WHERE 1=1` not caught** — those have a
  `whereClause` node (just trivially-true). Detecting tautological
  predicates is its own catch (post-1.0).
- **Single-fire on multi-stmt scripts** — only the first unbounded
  statement fires in v1. Documented above.
- **`INSERT ... ON CONFLICT DO UPDATE` not analyzed** — the ON
  CONFLICT update is a different AST shape (`InsertStmt.onConflictClause`)
  and isn't this catch's domain.
