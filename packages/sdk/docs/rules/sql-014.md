# SQL-014 — INSERT / UPDATE / DELETE without RETURNING

| | |
|---|---|
| **Severity** | `info` |
| **Confidence** | 50 |
| **Threat category** | `integrity` |
| **Default** | **OFF** (opt-in) |
| **Stable since** | `1.1.0` |

## Pattern

An `INSERT`, `UPDATE`, or `DELETE` statement has no `RETURNING`
clause, meaning the caller has no programmatic way to read back the
affected row(s) without running a follow-up query.

## Why this rule exists

AI agents commonly need the affected row back after a write — to
confirm a new id, to surface the updated state to the caller, to
chain a follow-up query. Without `RETURNING` the agent has to either:

- Re-query (costs an extra round-trip and tokens, and races on
  concurrency — the row may have been changed by another writer),
- Or proceed blind (which silently fails when the agent's downstream
  step assumes a known identifier).

Catching the missing-`RETURNING` shape gives the agent's pre-flight
loop a chance to add `RETURNING` and avoid both failure modes.

## Why this rule is OPT-IN by default

The SDK has no access to the agent's intent. We cannot tell whether
a given write was "I want the row back" vs. "fire-and-forget log
append." Default-on behavior would generate a sea of low-value `info`
catches on every legitimate write.

The rule is most useful when an agent's prompts routinely ask for the
affected row back ("create a user and tell me the new id"). Customers
in that workflow opt in explicitly:

```ts
import { analyze } from '@vibeguard-dev/local';

const result = analyze(sql, {
  rules: { 'sql-014': { enabled: true } },
});
```

Or for advanced consumers building custom rule pipelines:

```ts
import { runRules, parseQuery, RULE_REGISTRY } from '@vibeguard-dev/local';

const allRules = RULE_REGISTRY.map((entry) => entry.rule);
const result = runRules(parseQuery(sql).ast, allRules);
```

## Bug examples

```sql
-- Agent prompted "create a user and return the id"
INSERT INTO users (email) VALUES ('a@b.com');
-- ^ no RETURNING; agent must re-query by email and hope it's unique

-- Agent prompted "update the user's plan and confirm"
UPDATE users SET plan = 'pro' WHERE id = $1;
-- ^ no RETURNING; agent doesn't know whether the update affected 0 or 1 rows
```

## Correct alternatives

```sql
INSERT INTO users (email) VALUES ('a@b.com') RETURNING id, created_at;

UPDATE users SET plan = 'pro' WHERE id = $1 RETURNING id, plan, updated_at;

DELETE FROM sessions WHERE expires_at < now() RETURNING id;
```

`RETURNING` runs in the same transaction as the write, so there is no
additional round-trip cost or concurrency hazard.

## Detection approach

The rule walks the AST looking for:

- `InsertStmt` whose `returningList` is undefined / null / empty
- `UpdateStmt` whose `returningList` is undefined / null / empty
- `DeleteStmt` whose `returningList` is undefined / null / empty

For UPSERT (`INSERT ... ON CONFLICT DO UPDATE`), the rule checks the
outer `InsertStmt`'s `returningList`. If absent, the rule fires —
the agent still needs `RETURNING` on the outer statement to read back
what got inserted or what got updated by the conflict action.

For multi-statement scripts, the rule fires on the **first** matching
statement encountered.

## Confidence justification

**50.** Deliberately mid-range. The rule is correct that the SQL
lacks `RETURNING`, but whether that's a problem depends entirely on
the agent's prompt — information the SDK doesn't have. 50 reflects
"useful signal, but consumer judgment required."

## Known limitations

- **Cannot tell intent.** This is the load-bearing reason it's
  opt-in. The cloud product, which has access to the agent's stated
  intent, can make this judgment automatically; the OSS SDK cannot.
- **UPSERT inner action.** The rule only checks the outer
  `InsertStmt`'s `returningList`, not any per-action `RETURNING` on
  the conflict action. In practice this is the right answer
  (consumers always read the outer `RETURNING`), but it is a
  documented limitation.
