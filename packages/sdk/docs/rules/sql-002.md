# SQL-002 — Self-join without disambiguating predicate

| | |
|---|---|
| **Severity** | `warn` |
| **Confidence** | 70–85 (default 75) |
| **Threat category** | `integrity` |
| **Stable since** | `1.0.0` |

## Pattern

The same base relation appears two or more times in `FROM` (a self-
join), but the predicate connecting the table references either:

- doesn't exist
- is a tautology (`u1.id = u1.id`)
- is a same-column equality across aliases (`u1.id = u2.id`)

In none of those cases does the predicate actually disambiguate the
two roles the table is playing. The result is usually a duplicated
or otherwise meaningless join.

## Why it's dangerous

Self-joins are legitimate when a table is being joined to itself in
two distinct roles — e.g. an employees table joined as parent ↔
child for an org-chart query. The roles need to be expressed in the
predicate by varying *which column* connects them.

When an LLM forgets this, the predicate either tautologizes (matching
every row to itself) or compares the same column across both roles
(matching every row to its identical twin). Both produce wrong
results that are particularly hard to spot in casual review — the
query "works," it just returns nonsense data.

## Bug examples

```sql
-- Tautology — every row matches itself
SELECT *
FROM users u1
JOIN users u2 ON u1.id = u1.id;

-- Same-column equality — matches every row to its identical twin
SELECT *
FROM users u1, users u2
WHERE u1.email = u2.email;

-- No predicate at all — cartesian shape (also catches as SQL-001)
SELECT *
FROM users u1, users u2;
```

## Correct alternatives

```sql
-- Two distinct roles, joined on different columns:
SELECT child.id, parent.email AS manager_email
FROM employees child
JOIN employees parent ON child.manager_id = parent.id;

-- Or, if you genuinely want all-pairs of rows from the same table,
-- be explicit:
SELECT *
FROM users CROSS JOIN users;
```

## Detection approach

1. Walk to the first `SelectStmt`. Pull top-level FROM tables via
   `extractFromTables`.
2. Group by `relname`. Any group with size ≥ 2 is a self-join.
3. For each multi-group, build the set of identifiers (alias if
   present, else relname) for that group.
4. Walk every `A_Expr` in the JoinExpr `quals` and the `whereClause`.
   Classify each comparison:
   - **unrelated**: doesn't reference both group identifiers
   - **tautology**: both operands have the same alias
   - **same-column**: different aliases, same column name
   - **good**: different aliases, different column names
5. If any classification is **good**, suppress the catch for that
   group. Otherwise, fire.

The catch fires once per query (single-fire contract per Rule type).
Future enhancement: batch-fire on multi-group queries with multiple
disambiguation-less self-joins.

## Confidence justification

**Default 75 / range 70–85.**

Why 75 default? The AST signal is real (the relname-grouping is
unambiguous, the classification logic is conservative) but the
false-positive surface is non-trivial — same-column equality is
sometimes legitimate (e.g. finding rows that match on a uniqueness
key in a deduplication query).

Why range 70–85? Future minor versions can refine — e.g. raise to 80
when the predicate is a literal tautology (`u1.id = u1.id`), or
lower to 70 when the predicate is just same-column equality
(legitimate for deduplication-shaped queries).

## Known limitations

- **CTE shadowing** — A CTE name reused as a base-table reference
  produces an identical AST shape. The rule may fire on a legitimate
  CTE-self-join. Workaround: alias both references differently — the
  rule then evaluates the predicate.
- **Schema-aware grouping** — v1 groups by `relname` only. A query
  joining `public.users` to `private.users` (genuinely different
  tables under different schemas) groups them together. Documented
  trade-off; future enhancement could group by `(schema, relname)`.
- **Single-fire** — only the first multi-group fires per Rule call;
  documented in code comments and ROADMAP.
