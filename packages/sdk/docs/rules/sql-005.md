# SQL-005 — NULL comparison with `=` / `<>`

| | |
|---|---|
| **Severity** | `warn` |
| **Confidence** | 90–95 (default 95) |
| **Threat category** | `corruption` |
| **Auto-fix** | yes — `col = NULL` → `col IS NULL`; `col <>/!= NULL` → `col IS NOT NULL`. Source-text manipulation guided by the AST and string-literal masking, so `'= NULL'` inside a quoted string is left alone. |
| **Stable since** | `1.0.0` (rule); `1.3.0` (autofix) |

## Pattern

A binary comparison uses `=` (or `<>` / `!=`) with the SQL `NULL`
literal as one of the operands.

## Why it's dangerous

In SQL's three-valued logic, every comparison involving `NULL`
evaluates to **UNKNOWN**, which a `WHERE` / `HAVING` clause treats as
false. So:

```sql
SELECT * FROM users WHERE email = NULL;
```

…returns **zero rows** even when there are users whose email is
literally `NULL`. The LLM almost certainly meant:

```sql
SELECT * FROM users WHERE email IS NULL;
```

These two queries look indistinguishable at a glance but produce
opposite results. It's one of the most-cited footguns in SQL.

## Bug examples

```sql
-- Returns no rows — even rows where email is NULL
SELECT * FROM users WHERE email = NULL;

-- Same bug, different operator
SELECT * FROM users WHERE email != NULL;
SELECT * FROM users WHERE email <> NULL;

-- The footgun also bites inside CASE expressions
SELECT
  CASE WHEN deleted_at = NULL THEN 'active' ELSE 'inactive' END
FROM users;
```

## Correct alternatives

```sql
-- IS NULL / IS NOT NULL — the standard NULL-aware predicates
SELECT * FROM users WHERE email IS NULL;
SELECT * FROM users WHERE email IS NOT NULL;

-- NULL-safe equality between two values (treats NULL = NULL as true):
SELECT * FROM users WHERE email IS NOT DISTINCT FROM normalized_email;
```

## Detection approach

The rule walks every `A_Expr` node in the parsed AST and fires when:

1. The `kind` is `AEXPR_OP` (regular binary operator), AND
2. The operator name is `=` or `<>` (libpg-query normalizes `!=` →
   `<>` at parse time), AND
3. Either operand is `A_Const { isnull: true }` (the SQL NULL literal)

The rule **never** fires on:

- `IS NULL` / `IS NOT NULL` — those are `NullTest` nodes, not
  `A_Expr` nodes; the AST shape is structurally different
- `IS DISTINCT FROM NULL` / `IS NOT DISTINCT FROM NULL` — those are
  `A_Expr` nodes with `kind: AEXPR_DISTINCT` (not `AEXPR_OP`)
- `NULLIF(col, sentinel) = 'y'` — the NULL token here is internal to
  the NULLIF function call, not a direct comparison operand

The catch fires on the **first** `=NULL` / `<>NULL` it finds (single-
Catch contract per `Rule` type). Multiple NULL comparisons in the
same query produce one Catch in v1; future enhancement is documented
on the roadmap.

## Confidence justification

**Default 95** — the AST signal is unambiguous (operator + literal-NULL
operand), and the only legitimate use is intentionally testing
3-valued-logic behavior, which is rare and almost always done in a
test harness, not production code.

**Range 90–95** — leaves room for future minor versions to drop to 90
in narrow cases where the rule's heuristic might mis-classify (e.g.
operator overloading, parser-version edge cases). For 1.0 the rule is
purely structural; 95 is the default.

## Known limitations

- **`IN (NULL, 1, 2)` not flagged** — the NULL inside an IN-list is
  inside a list, not a direct comparison operand. That pattern has
  similar but not identical semantics; it's a candidate for a sibling
  catch if there's pull (post-1.0).
- **Single-fire on multi-occurrence** — only the first NULL
  comparison fires per Rule call. Documented above.
